# KNode V3 Project Data Format

This document describes the confirmed V3 format. V3 is the only supported project format and supersedes the V1 and V2 structures described in earlier development documents. Migration from older formats is unsupported, and KNode does not read legacy layout fields. If the version is unsupported, the JSON is malformed, or validation fails, KNode rejects the open or save operation and leaves the original file intact.

## Project Structure

The root object contains exactly these fields.

- `format` is the existing format signature, `"forest-project"`.
- `version` is the only version field and must be `3`. It replaces `schemaVersion`.
- `projectId` is a stable UUID that survives project renaming.
- `name` is the project name.
- `nodes` is the single project-wide array of nodes.
- `views` contains exactly `tree` and `graph`.

The TypeScript and Rust tests share the same complete, executable JSON example. [View the V3 example fixture](../../../tests/fixtures/project-v3.json).

## Nodes and Views

Each node contains `id`, `title`, `parentId`, `progress`, `weight`, and `color`. The `linkedPaths` field is optional.

A node `id` must be 1–128 ASCII characters, using only letters, digits, underscores (`_`), and hyphens (`-`). Windows reserved names such as `CON`, `NUL`, and `COM1` are rejected. Node IDs must be unique across the project, ignoring case.

`progress` stores the manually entered value and must be a finite number from 0 to 100, inclusive. Fractional values are allowed. `weight` is a nonnegative safe integer. If a node has children with positive weights, KNode recursively computes their effective progress and takes a weighted average. Otherwise, it uses the node’s own manual progress. The node’s own weight affects only its contribution to its parent’s progress and whether its progress bar is shown.

`color` stores a six-digit hex color independently for each node. New nodes default to `#6c9661`. Older V3 projects may use `null`. On open, KNode restores the previous display color in memory and writes it on the next save.

Keep `position`, `collapsed`, `documents`, internal file listings, computed progress, and Vue Flow runtime fields out of node objects.

The `tree` object contains exactly these fields.

- `positions` maps every node ID to `{ x, y }` and rejects unknown IDs.
- `collapsedIds` is an array of unique existing node IDs. It only controls the visibility of descendants in Tree View.
- `viewport` stores `{ x, y, zoom }`.

The `graph` object contains exactly these fields.

- `positions` maps node IDs to `{ x, y }`. The keys define graph membership. The map can be empty or contain a subset of the project’s nodes.
- `edges` is an array of `{ id, source, target, direction, label? }` objects. Both endpoints must have entries in `graph.positions`. An edge `id` follows the same character, length, and Windows name rules as a node ID. Edge IDs must be unique within `graph.edges`, using a case-sensitive comparison.
- `viewport` stores `{ x, y, zoom }`.

`direction` accepts only `forward`, `both`, and `undirected`. Self-loops, cycles, multiple incoming or outgoing edges, and parallel edges are allowed.

`label` is optional. When present, it must be nonempty text, at most 200 UTF-16 code units long, and free of control characters. It cannot be `null`.

Each view persists its own `positions` and `viewport`. The active view is runtime state. Coordinates must be finite numbers with an absolute value of at most `1e9`. The inclusive zoom range is `0.2` to `2.5`. All objects reject unknown fields.

## Operation Semantics

- `parentId` defines the tree forest. It allows multiple roots and at most one parent per node. Self-parenting and parent-child cycles are forbidden.
- Graph edges have no effect on tree progress or `parentId`. Both views use each node’s own color.
- Creating a node in Tree View assigns positions in both views and adds no graph edges automatically.
- Creating a node in Graph View adds it as a root in Tree View and assigns separate positions in both views.
- Both views share all project nodes. There is no separate command to remove a node from Graph View.
- On opening an older V3 project, KNode preserves the existing graph positions, edges, and viewport and assigns positions to nodes missing from the graph. These positions are filled in memory first and written on the next manual save or when an edit triggers autosave.
- Deleting a node removes its references from both views. Internal files are retained under the existing rules, and undo can restore the node.
- Undo records changes to node data, both view layouts, tree collapse state, and graph edges by operation. Viewport navigation in either view stays outside undo history. The default history limit is 100 entries.
- Copying in Tree View preserves parent-child relationships within the explicit selection. Pasting a Graph View selection creates new root nodes and a new graph layout for the selection. It remaps only edges within the selection and leaves the original graph intact.

## Disk Storage and I/O

A project folder contains a JSON file with the same name. Internal files go into `Nodes/<nodeID>/` as needed and are omitted from the JSON manifest.

The desktop app limits project JSON to 32 MiB (33,554,432 bytes) when reading or saving. Reads use the file size on disk. Saves use the size of the UTF-8 JSON in bytes.

External files are referenced by `linkedPaths`. Editing either view leaves the external originals in place and does not copy or delete them. Omit `linkedPaths` when there are no external links. When present, it must be a nonempty array of strings that meet these rules.

- Each path must be 1–4,096 UTF-16 code units long. Supported forms are paths relative to the project folder, absolute paths with a drive letter (such as `D:/资料/说明.md`), and UNC paths with a server and share name (such as `//server/share/说明.md`). Either `/` or `\` can serve as the separator. A colon is allowed only after the drive letter in an absolute path. Forms such as `D:说明.md` and `/说明.md` are rejected.
- Except for `.` and `..`, each path component must pass Windows filename validation and is limited to 240 UTF-16 code units. Empty components, trailing dots or spaces, control characters, invalid characters such as `<>:"|?*`, and Windows reserved names are rejected.
- Within a single node, paths must be unique after normalization. The duplicate check standardizes separators, ignores case, skips `.` segments, and collapses `folder/..` where possible. When you add or relocate a link through the UI, Rust also deduplicates paths that resolve to the same filesystem target.

Project creation, opening, saving, and renaming use the same Rust V3 validator. File operations that read project data use that validator as well.

Frontend parsing, JSON export, autosave, and saving before close all use the V3 model and validator.

Autosaves run in sequence. KNode syncs a temporary file before replacing the destination, checks for external changes, and applies filesystem protections to project files and directories.

When a project is open, the title bar provides icon buttons for Tree View and Graph View. The app and `ForestCanvas` share one view controller, with `tree` as the default. Switching views creates no undo entry. The active view stays outside the project JSON.

Earlier specifications and development reports are historical records. Use the linked V3 fixture when creating current projects.

## On-Demand Auto Layout

Auto layout uses the existing `moveViewNodes` function to update `positions` for the active view. Node data, `parentId`, `edges`, and `collapsedIds` remain intact. Each applied layout creates one undo entry.

Hidden descendants in Tree View keep their positions and are excluded from layout. Fitting the view uses the existing canvas navigation and adds no layout history entry. The app stores layout directions separately for Tree View and Graph View in `localStorage` under `knode-layout-directions`. These preferences stay outside the project JSON.
